# 팀 작업 가이드 (병렬 개발 규칙)

## 한 문장 요약
폴더를 나눠서 건드리는 파일이 겹치지 않게 하고, 계약과 샘플 데이터로 서로의 완성을 기다리지 않게 하고, 매일 작게 머지해서 `main` 이 항상 돌아가게 한다.

## 왜 병렬이 되는가
| 장치 | 역할 |
|---|---|
| `src/contracts/` | 함수 입출력 형식이 고정되어 있어 서로 다르게 해석할 일이 없다 |
| 스텁 + `pipeline.py` | 부품이 아직 가짜여도 질문→답변이 끝까지 돈다. 내 스텁만 진짜로 바꾸면 된다 |
| `fixtures/` | 앞 단계 모듈이 없어도 샘플을 입력으로 내 모듈만 개발·테스트할 수 있다 |
| 폴더 소유권 | 서로 다른 파일을 고치므로 충돌이 거의 없다 (`AGENTS.md` 표 참고) |

## 하루 흐름 (예: P2)
```
git pull                                   # 아침에 최신 받기
git checkout -b p2/input-guard-v0          # 내 브랜치
# 코딩 에이전트와 작업 (AGENTS.md 를 먼저 읽게 하고, 내 폴더 안에서만)
python -m pytest                           # 전체 테스트 통과 확인
git diff --stat                            # 수정한 파일이 모두 내 폴더 안인지 확인
git push  ->  PR 올리기  ->  팀원 1명이 훑어보기  ->  main 에 머지
```
- `main` 에는 **하루 1회 이상** 머지한다. 브랜치를 오래 묵히면 나중에 합칠 때 어긋난다.
- 반쯤 된 상태라도 기존 테스트를 깨지 않고 스텁 대신 쓸 수 있으면 머지한다.
- 에이전트가 만든 코드도 다른 사람이 한 번 훑는다. **API 키가 섞이는 사고**를 특히 조심한다.

## 충돌이 날 수 있는 3곳
| 파일 | 규칙 |
|---|---|
| `settings.yaml` | 섹션 단위로 내 부분만 수정 |
| `requirements.txt` | 맨 아래에 한 줄씩 추가만, 머지 전에 pull |
| `src/contracts/` | 직접 수정 금지. P3에게 요청 → 합의 → P3 반영 → `CONTRACT_VERSION` 올리고 공지 |

## 통합일 체크리스트 (11/8, 11/11, 11/13)
1. 각자 PR 을 머지하고 `main` 을 받는다.
2. `python -m pytest` 전체 통과.
3. `python -m eval.run_eval` 로 비교표를 갱신해서 공유 문서에 붙인다.
4. 어긋나는 부분을 모아 담당자에게 배정한다 (원인 라벨: input-guard / retrieval / grounding / tutor / false-positive).
5. 원인이 두 모듈에 걸치면 P3가 조율한다.

## 일정이 밀릴 때 자르는 순서
1. 시간 남으면 하려던 것 (진단 퀴즈, 학습자 상태 화면, 카드뉴스·개념도, 자유 노트 확인, 관심사 연관 키워드 제안)
2. 튜터 자동 분석, 확인 질문 채점 (수동 버튼으로 대체)
3. 프레임워크(NeMo / Guardrails AI) 비교
4. **절대 자르지 않는 것**: 4단계 비교표, 오탐률 측정, 홀드아웃 측정, 주장-근거 일치 검증

## 막혔을 때
| 상황 | 대처 |
|---|---|
| 데이터가 아직 안 옴 | 임시 데이터로 진행하고 형식만 맞춰 두기. 접근 문제는 오늘 안에 운영 사무국(KOSA)에 문의 |
| 한 모듈이 늦어짐 | 그 모듈은 스텁으로 둔 채 통합하고 완성되면 교체 |
| AI 판단이 들쭉날쭉 | 임계값을 올리고, 출력을 JSON 으로 고정하고, 애매하면 안전한 쪽(보류)으로 |
| 크레딧이 빨리 줄어듦 | `llm.cache` 사용, 작은 모델과 `--limit`, 전체 평가는 통합일에만 |
